# Bug & inconsistency audit — Headwinds and Tailwinds
**2026-08-12 · report only, no code changed**

## Scope and method

Both trees as they sit on disk (HW at `8bd133c`, TW at `917597b` plus 51 uncommitted marketing-page edits). Six parallel finder agents — engine economics, MP/server correctness, UI⇄engine agreement, Tailwinds-specific, TW↔HW drift, data integrity + crash surface — then three adversarial verifiers whose brief was to **refute** the top fourteen claims. Everything below survived that pass. Claims that did not survive are listed at the end, because two of them were about to be wrong in an expensive direction.

Findings are tagged **[HW]**, **[TW]** or **[BOTH]**. `path:line` is relative to each repo root; HW engine paths are under `packages/engine/src/`, TW's twins under `src/`.

| Severity | Count | |
|---|---|---|
| CRITICAL | 5 | live money/traffic errors on the main path |
| HIGH | 19 | wrong numbers a player acts on, or free value |
| MEDIUM | 24 | inconsistencies, server hardening, data |
| LOW | 14 | cosmetic, dead code, latent |

Two structural notes before the list:

**The tick and the previews have diverged in opposite directions.** `pairShare.js` (the preview helper) has a dedupe the tick lacks; `simulateRoute` has a competitor bank `simulateTagRoute` lacks; `Finance` has a bare sim `Routes` doesn't. Five of the six worst findings are one of those three seams.

**Tailwinds is no longer behind Headwinds.** `tools/sync-from-tailwinds.mjs` hard-exits at line 39 ("Tailwinds is NO LONGER authoritative"), and since then TW has landed four fixes HW never got — `rivalOffersFor`, the tag-route competitor bank, the acquisition floor, and `brandReach` in the share panels. Porting is now a two-way job.

# CRITICAL

### C1 — [HW] Every human rival is counted twice in the weekly tick
`utils/simulation.js:1502-1511` (single-aircraft) and `:3387-3395` (pooled) · `apps/headwinds-server/src/lib/humanRivals.mjs:420-425` · **the fix already exists at `models/pairShare.js:176`**

`buildRivalViews` walks `active` once and pushes each rival into **both** `competitors` (with `routes[key]` populated) **and** `humanRivals[key]` (an encroachment spec carrying the same `competitorId`). `simulateRoute` concatenates the two lists blind, so `computeMarketShare` scores every rival as two airlines. `buildEncroachmentOffer` publishes as `encroach:human:a2` while `buildCompetitorOffer` publishes as `human:a2`, so nothing collides and the softmax has no way to notice.

The preview helper already knows: `pairShare.js:176` reads `if (c.human) continue; // already counted via humanRivals`, and the surrounding comment names the exact consequence. The tick never got the same line.

**Measured** (two real airlines through `buildRivalViews → withRivals → ADVANCE_WEEK`, the chain `tickService.mjs:155` runs):

| fares / freq | tick pax | correct pax | loss |
|---|---|---|---|
| 170/150 ×14 | 237 | 379 | **−37.5%** |
| 200/200 ×10 | 127 | 220 | **−42.3%** |
| 140/190 ×7 | 611 | 913 | **−33.1%** |

Load factor 12.5% vs 20% — not a capacity artefact. Every player on every contested pair loses a third of their traffic and revenue, symmetrically, and world-wide booked pax exceed the demand pool. With N rivals the player is scored against 2N offers, so it worsens as a world fills up. `projectRouteAddition` (`pairShare.js:439`) passes `rivalSpecsFor` *and* `state.competitors`, so it double-counts too — meaning the two previews disagree with each other as well as with the tick.

### C2 — [HW] `BUY_HEDGE` takes an unvalidated `coverage`; two contracts make fuel cost negative
`reducer.mjs:4682` · `apps/headwinds-server/src/lib/decisionGuard.mjs` (no case; `:362 default: return payload`) · `apps/headwinds-server/src/world.mjs:59` (allow-listed) · `utils/fuel.js:137`

`BUY_HEDGE` is allow-listed, costs no cash, has no guard, and stores `action.coverage` verbatim. `assertFinitePayload` only rejects non-finite numbers and `|v| > 1e10`. `effectiveFuelMultiplier` divides by the **signed** sum of coverages, and the `rawCoverage <= 0` guard at `fuel.js:139` doesn't fire when the sum is a small positive.

Two contracts of **different durations** (same duration only gives 1.01):

```

POST {type:'BUY_HEDGE', payload:{durationId:'short', coverage:1000.1}}

                 baseline    exploited
fuelMultiplier   1           -68.997
```

Both accepted 201, free. From the next tick every pax, tag and cargo route books a large negative fuel cost; a one-aircraft airline turns a losing week into ~$1.8M profit, and it scales with fleet size and persists 8–26 weeks. SVPS is the leaderboard metric, so this destroys a world's standings.

### C4 — [HW] The fare editor is fare-blind on any pair you fly with two or more aircraft
`models/pairShare.js:94` and `:410-412` · `src/components/Routes.jsx:2066-2077`

`buildPlayerPairOffer` reads `state.routePricing?.[key] ?? r0.classPrices ?? {}` — the **stored** fare wins — and `routePricing` is the declared single source of truth (`reducer.mjs:677`, written on every `ADD_ROUTE`), so the fallback never fires. On a pair with ≥2 tails, `projectRouteAddition` then slices a `demandOverride` out of that stale-fare pooled result and `simulateRoute` simply multiplies the frozen pax count by the draft fare.

`replacesRouteId` **is** passed and the edited route **is** excluded — it doesn't help, because `others` still holds one route and `pairRoutes.length === 2`.

```
2 tails, STORED $300, drag the DRAFT fare:
  $120 -> pax 460  LF 17.4%  rev $110,400
  $300 -> pax 460  LF 17.4%  rev $276,000
  $700 -> pax 460  LF 17.4%  rev $644,000      <- pax frozen, revenue exactly linear

1 tail control, same drag:
  $120 -> pax 2646 LF 100.0%
  $300 -> pax  914 LF  34.5%
  $450 -> pax    0 LF   0.0%                   <- correct elasticity
```

And the causal proof — hold the draft at $300, move only the stored fare: pax goes 2646 → 1480 → 460 → 0. The panel responds to the fare the player is *not* editing and ignores the one they are. LF 17.4%, so no capacity cap involved. The one screen whose entire job is "what does this fare do?" promises unbounded profit from raising fares.

Scope: the launch forms (`RoutePlanner.jsx:474`, `Routes.jsx:2362`) lock fares to the stored pair price, so draft ≡ stored and nothing shows there. This is `PricingPanel`/`FareEditor` only.

### C5 — [TW] The route-launch forecast ignores your own existing service on the pair

### H2 — [HW] A tag route and a nonstop on the same O&D each draw the full demand pool
`utils/simulation.js:3267` — `if (isMultiStop(route)) continue;` in the pooling pre-pass

The comment says "tag routes self-contain their O&D split", which is true *within* one rotation and does nothing to stop the tag route's segment demand being claimed again by your own nonstop on the same pair.

### H10 — [BOTH] Capacity is charged twice: the load models are handed already-capped demand
`utils/simulation.js:1545` (`directionalLoadMultiplier`) and `:1531` (`nwrDemandScale`)

`directionalLoadMultiplier(demandOneWay, capacityOneWay, skew)` applies `min(demand, capacity)` itself, so it must receive **uncapped** demand. It is passed `leisurePax + businessPax` from `demandResult`, which `computeMarketShare`/`_monopolyResult` already capped at `totalSeats`. It is therefore permanently in the `D ≤ C` regime and returns `1 − skew/2` on any full aircraft — it can never distinguish "demand equals capacity" from "demand is 10× capacity", which is the only case where the haircut is wrong.

JFK–CUN in August, 737 MAX 8 at 7×/wk (1,470 seats), pool 14,087 one-way (9.6× capacity, so both directions saturate and the correct multiplier is exactly 1.0). Engine computes 0.8646 and books 1,272 pax / $767,596 instead of 1,470 / $882,000 — **198 pax and $114,404 destroyed every August**, on a route the model itself says should lose nothing.

`nwrDemandScale` (`market.js:690`) has the same shape and the same input. Its header promises "deep-oversubscribed routes asymptote to the ceiling; a route at demand ≈ capacity lands ~87%" — those two cases collapse into one and the 95% ceiling is unreachable. JFK–LAX at 13× oversubscribed returns LF 0.8837 instead of ~0.95: **$50–95k/wk per fat route**. Directly verified: `nwrDemandScale` at true D=3,000 / C=1,000 gives 0.9493; the coded (capped) path gives 0.8733.

Almost certainly one fix — pass the uncapped pool to both.
